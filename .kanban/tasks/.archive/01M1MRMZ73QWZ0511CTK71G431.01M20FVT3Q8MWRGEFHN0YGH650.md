### What

cli-plan.md §11.1, which named a concrete task and gave it no card. It
is the decider for §11.3 — whether the CLI ever needs a shared server.

The whole `serve` mode of §11.3, a unix socket transport in the wire
package and a multi-connection agent, exists only if this measurement
says the per-invocation load cost is real. Measure before building any
of it.

**This card is a measurement, not a feature.** It writes no product
code, and it writes no test. The evidence is a comment on this card.

**What decides the question.** A daemon loads the model weights ONCE.
Without it, each `acp-agent run` starts a process, pulls the weights
into memory and onto the GPU, answers, and ends. So the saving a daemon
gives is the **per-invocation load cost**, and each run pays it.

**The measurement:**

1. Run `acp-agent run "hello"` three times, and record each wall time.
2. Split each wall time into resolution and generation, from the
   `ResolutionProgress` phases, so a slow answer is not confused with a
   slow load.
3. Record the median.

Record the numbers in a task comment, and write a one-paragraph verdict:

- **The load cost is small** — one binary is correct, `serve` is waste,
  and §11.3 is closed. Say so, and the plan drops the section.
- **The load cost is large** — a daemon pays for itself on the second
  run. Then raise the cards §11.3 describes: a socket transport in the
  wire package, and a multi-connection agent.

- [ ] Time three runs, and record each
- [ ] Split resolution from generation
- [ ] Record the numbers and the verdict in a task comment

### Acceptance Criteria

- [ ] A task comment holds three timings, the median, and the machine
      and model they were taken on.
- [ ] The comment states the resolution/generation split.
- [ ] The comment states one verdict, in one paragraph, and names the
      next step for each branch.
- [ ] No product code changes, and no test is added.

### What this card does NOT do, and why

**No cold page cache, and no `sudo purge` or reboot.** An earlier
version of this card asked for a cold-cache timing. It is dropped. The
cold read is a one-time cost after a boot, and a daemon must pay it too,
so it does not separate the two designs. The per-invocation load cost
does.

**No stored benchmark.** An earlier version asked for
`ColdLoadBenchmark.swift`, a test that asserts nothing about a duration.
A test that asserts nothing is not a test, and a timing belongs in a
record and not in the suite. The measurement is a one-off, run by hand.

**No download timing.** The time to fetch weights from the network is
not part of this question.

### Blocked by

The new defaults, so the measurement is taken on the profile that ships.
