title: Send the terminal updates of a shell run on the joined SDK tool-call id
---
## Problem

Task ^e1yq4gh sends each run update (progress, display, report, settlement) on the SDK tool-call id that Router joins to the completion token of the run. `TerminalStream` is out of scope of ^e1yq4gh. `TerminalStream.announceRunIfNew(_:)` still sends its `tool_call_update` (the `Terminal` reference, `in_progress`) on `ToolCallId(rawValue: commandID)`, and the `commandID` is the completion token. Thus a shell run with live output still gives the client a second tool call: one on the SDK id and one on the completion token.

## Facts

- `TerminalStream` reads the host-owned `ShellOutputChunkStream`, not the `SessionEvent` stream, so it does not see the `toolInvocation(record, toolCallID:)` join.
- `EventProjection.joinedToolCallIds` holds the join for one prompt. It is private to the projection.
- The terminal id (`TerminalId(rawValue: commandID)`) and the terminal item of the settlement can stay the completion token. Only the `toolCallId` of the announce update must change.

## What to change

- Give `TerminalStream` the join (for example, a shared join table that the projection writes and the terminal stream reads), so that the announce update goes on the joined SDK id when one exists, and on the completion token when none exists.
- Keep the order problem in mind: a terminal chunk can arrive before the projection handled the open record. Do not send the announce on the token and later on the SDK id.

## Acceptance

- [x] A shell run with live output gives exactly one `toolCallId` on the wire: the SDK id.
- [x] A shell run that no SDK call joined still gets its announce on the completion token.
- [x] A test reads the wire messages of one shell run and counts the distinct `toolCallId` values.
