### What

`aToolListChangeIsStagedAndAppliesOnlyAtTheNextTurnBoundary()` fails in each full `swift test` run. The test wins a wall-clock race when it runs alone, and loses that race when the full suite runs. Remove the race.

1. The test is at `Tests/FoundationModelsACPAgentTests/MCPCompositionTests.swift:424`. Two assertions record an issue:
   - `MCPCompositionTests.swift:438` — `#expect(!initial.contains(Self.greeterPath))`
   - `MCPCompositionTests.swift:446` — `#expect(!beforeTick.contains(Self.greeterPath))`

2. Each full `swift test` run fails. Three runs gave 3, 3 and 4 issues, and one of those issues in each run is the known `withKnownIssue` at `Tests/FoundationModelsACPAgentTests/Support/HarnessSmokeTests.swift:239`. The other issues are always these two assertions.

3. The test passes when it runs alone. Three runs of `swift test --filter 'MCPCompositionTests/aToolListChangeIsStagedAndAppliesOnlyAtTheNextTurnBoundary'` each passed.

4. The cause is a fixed timer in the scripted server. `FoundationModelsMultitool`, in `Tests/Support/MCPTestServer/DynamicToolsetScenario.swift`, sets `dynamicToolsetStageDelayMilliseconds = 1500` (line 25) and schedules each stage with `scheduleMutation(after: dynamicToolsetStageDelay * (index + 1), stage)` (line 114). Stage 1 adds the `greeter` tool and sends `tools/list_changed`.

5. Thus the test has 1500 ms to start the subprocess, complete the MCP handshake and make its first `helpPaths` read. A full run keeps the machine busy, the first read comes after stage 1 fires, and the greeter is already in the catalog. The two assertions then fail.

6. Change the test to prove the property that its name states: a tool that the server adds becomes visible in the mounted surface only after `turnWillBegin()` runs. The test must not assume which stage has fired when it makes its first read.

7. Do not change `FoundationModelsMultitool`. It is a family package, and a change there needs a card on that project first. Make the correction in this repository.

### Test shape

- The test shows that a change to the server's catalog is not visible in the mounted surface until `turnWillBegin()` runs.
- The test does not use a wall-clock delay to decide if it passes.
- The full `swift test` run passes three times in sequence, with the one known issue at `HarnessSmokeTests.swift:239` and nothing else.
- The test still passes when it runs alone.
