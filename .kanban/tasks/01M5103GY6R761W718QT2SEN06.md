Found in task ^az53ay4. The relay keeps a completion (`earlyCompletions`) or an end (`earlyEnds`) that comes while it waits for `session.respond` of an accepted URL answer. When Router then records the accept, the relay sends `elicitation/complete` at once. No test covers these two paths: a fixed-order test needs a hold point in `respond`, for example a `CloseCountingRoutedSession` that holds `respond` until the test releases it. Work: add a fixed-order test for each path; each must fail when the early path is removed. #elicitation-phase-3

## Done (2026-10-15)

- `ElicitationRelay.holdAfterRespond(_:)`: an internal hold that runs after `session.respond` returned and before the round trip reads the delivery. It is `nil` in production. While the hold waits, the relay actor is free, so a completion or an end reaches the relay before the round trip knows of the accept.
- Tests (fixed order): the hold opens a gate when it starts; the test then completes the flow (`RunPlane.complete`) or cancels the run (`RunPlane.cancel`), and waits for the debug record of the early path. No completion is at the client in the hold. The test then releases the hold, waits for the end of the elicitation span, and sends a marker update through `commandSink`. The client reads notifications one at a time in arrival order, so when the marker is there, the completion is there too.
  - `aURLCompletionWhileTheRelayWaitsForRespondSendsOneCompletionAfterTheAccept`
  - `aRunCancelWhileTheRelayWaitsForRespondSendsOneCompletionAfterTheAccept`
- With the early path removed (`guard false`), both tests fail on the completion check.
