Step lead request, elicitation phase 3 (elicitation-plan.md task 8). Send the design to the step lead first.

Problem: ElicitationRelay calls completeURLFlow at once after an accepted URL answer (the `.acceptedAwaitingCompletion` delivery). Thus `elicitation/complete` goes to the client at consent, not at the end of the URL flow.

Work: the relay sends `elicitation/complete` only when the URL flow ended. The design names the event that says that a URL flow ended, how it reaches the relay, and what the relay sends then. A change in Router or Extras is a follow-up card on that project; this task changes only ACPAgent.

Tests: fixed order, fail on the old code. #elicitation-phase-3

## Done (2026-10-15)

Upstream: Extras e65287a, Router 61d5711 (`SessionEvent.elicitationCompleted`).

- `ElicitationRelay`: on `acceptedAwaitingCompletion` the relay keeps the id as awaiting completion. It sends no `elicitation/complete` and does not call `session.complete`. The id stays outstanding for the uniqueness duty.
- `ElicitationRelay.complete(_:)`: on `elicitationCompleted` for an awaiting id, the relay sends `elicitation/complete` one time and releases the id. A completion that comes while the relay waits for `respond` is kept, and the round trip sends `elicitation/complete` when Router records the accept.
- `ElicitationRelay.end(_:)`: on `elicitationEnded` for an awaiting id, the relay also sends `elicitation/complete`. An end that comes while the relay waits for `respond` is kept the same way.
- `drainOpenRoundTrips()` releases each awaiting id with a warning and sends nothing.
- `ACPEventTranslator` has the case `.elicitationCompleted` and waits for the relay, so `elicitation/complete` goes out before the events of the resumed run. `SessionProjector` wires the handler.

Tests (fixed order; the fixed point after the accept is the end of the elicitation span):
- `aURLElicitationCompletesOnlyWhenItsFlowCompletesAndNotAtTheAccept`: no completion at the accept; `RunPlane.complete(elicitationId:)` gives `.completed`; then one completion. It replaces `aURLElicitationCompletesAfterAcceptAndTheCompletionReachesTheClient`.
- `aRunCancelAfterAURLAcceptSendsOneCompletion`: no completion at the accept; one completion after a run cancel.
- Both fail on the old code.

Not tested: the early-completion and early-end paths (a completion or an end while the relay waits for `respond`). A fixed-order test needs a hold point in `respond`. Card ^t2sen06.
