### What

cli-plan.md §5.7. The default profile is large and nothing is on disk on
a clean machine, so the first `acp-agent run "hello"` downloads
gigabytes. A person who asks for a haiku and gets a silent terminal for
ten minutes concludes the tool is broken. **Progress is not decoration
here. It is the difference between working and appearing hung.**

`--verbose` and `--quiet` are a separate card. This one draws the
resolution bar and nothing else.

Router supplies the data: `ResolutionProgress` carries the `phase`, a
`fraction`, per-slot `bytesDownloaded` and `bytesTotal`, and
`RoutedACPAgent.init` already takes `reporting: ResolutionProgress?`.

**The two hard parts, which are where this task will fail:**

1. **`ResolutionProgress` is `@MainActor @Observable`.** Every read of
   `phase`, `fraction` and `slots` is a main-actor hop. Plan the
   reporter around that; do not discover it late.
2. **`RoutedACPAgent.init` performs the whole resolution inside `init`**
   (`RoutedACPAgent.swift:141-148`). So the bar cannot be driven after
   construction returns. Start a concurrent task that observes the
   progress object **before** that `await`, and tear it down after it.
   The progress object is created first and passed in.

In `Sources/acp-agent/ProgressReporter.swift`, drawing through
`TerminalRenderer`:

| Condition | stderr shows |
|---|---|
| The renderer says the destination is a terminal | The phase, the slot, and a bar with the bytes |
| Not a terminal | Nothing |

The bar is erased when the first answer chunk arrives. Nothing here
touches stdout, so §5.6 stays byte-exact.
