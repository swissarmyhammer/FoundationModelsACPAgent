## The measurement

The first 227 seconds of `django__django-13447`, in the run of 2026-09-13, on
an Apple Silicon machine with `mlx-community/Qwen3.8-27B-mxfp4`:

| Measure | Value |
|---|---|
| Elapsed | 227 s |
| Shell execution | 2.2 s |
| Model generation | 225 s, which is 99% |
| Distinct operations | 20 |
| Seconds of each operation | 11 |

The commands are free. The model is the whole cost. So the speed of a run is
the COUNT of the model turns, and nothing else.

## The problem

Each operation costs two model turns, and not one. The tool answers with a
pending envelope:

```json
{"pending": true, "completionToken": "01M2E0874P503JZGBPEP4SD2JT",
 "next": "Do not answer yet, and do not guess the result. Call the wait tool
 with completionToken ... "}
```

The model must then generate a second call, to `wait`, only to collect an
answer that is ready already. The shell command of that example took 19 ms.
The round trip around it took 52 s.

## What to look at

- Give a result that is ready at once, and keep the pending envelope for an
  operation that is truly slow. A command of 19 ms must never cost a turn of
  the model.
- Or let the tool hold the answer for a short time before it gives the
  envelope, so a quick command answers in one turn.

## When it is complete

- A quick command costs ONE model turn.
- A measurement of the same instance shows the count of the operations, and
  the count of the model turns, and the second is no longer twice the first.
