### What

The agent does the whole job through `acp-agent run`. The tier-4 eval,
on the same model and the same machine, makes no token at all. So the
defect is in the eval harness and not in the product.

**That last sentence is wrong, and the measurement below shows it.** The
eval's own prompt, sent through the CLI, hangs in exactly the same way.
The defect is in the product.

### Measured on 2026-09-08, on `mlx-community/Qwen3.8-27B-mxfp4`

**The CLI works.** `acp-agent run --verbose --cwd <dir> "Read the file
marker.txt and tell me exactly what it says."`

```
EXIT=0
stdout: `marker.txt` contains exactly one line:
        ```
        hello from the probe
        ```
stderr: tool call_… completed searchTools
        tool call_… completed runCode
        tool call_… completed wait
        (twice over)
        stop end_turn
```

It read a real file, ran the whole `searchTools` to `runCode` to `wait`
chain, answered correctly, and left with exit 0.

**The eval hangs.** The same model, driven by
`PythonCLIEvaluationTests`, made no fragment at all:

```
session 01M2176C6N076KW9APHRCY0H0M:
generation has produced no fragment in 390.1s (0 so far, 390.1s in flight)
```

A run under the `4bit` default hung the same way for 3120 seconds. The
`4bit` default was a true defect and `^s0bw5cv` corrects it, but this
card is a SECOND defect: `mxfp4` answers through the CLI and still hangs
under the eval.

### The answer

Candidate 1 of the three below carries it. The eval's own `greet`
prompt, sent through the shipped CLI, ends with `stop _stalled` at 120
seconds. The harness composition is NOT the difference.

The one difference is **the time to the first observable output**, and
two ceilings cut it off. Each ceiling alone ends the sample:

- `PromptTurn.stalledGenerationBound` was 120 seconds. The measured time
  to the first tool call on a build prompt is 555 seconds.
- `evalSampleIdleCeilingSeconds` was 300 seconds. One whole sample takes
  658 seconds through the suite, and about 3100 seconds through the CLI
  on a loaded machine.

Router's fragment count is a false witness beside them: through a whole
successful turn the stall report kept saying `0 fragments` at 1780
seconds in flight, while `runCode` and shell calls were completing and
files were landing on disk. So `sawOutput` is the only honest signal the
guard holds, and the bound must stand clear of the window before the
first output.

### Tests

- [x] The eval harness composes the agent through the same path the CLI
      uses, or the card states why it must not and what it does instead.

It does not, and here is why. `AgentComposition.compose(workingDirectory:
environment:)` takes no `userDirectory` and no `recordingsDir`, and the
eval needs both: it injects a throwaway user layer so no run reads the
person's own configuration, and it switches Router's recorder on so the
`toolTraffic` grader has a transcript to read. So the eval keeps its own
wiring.

The measurement clears that wiring of this defect. The eval's own prompt,
sent through the SHIPPED composition path, hangs in exactly the same way,
and the same prompt answers through both paths once the two ceilings
stand clear of the first output.

1. **The prompt.** MEASURED, and it carries the answer. The eval's own
   `greet` prompt through the CLI: `stop _stalled` at 120 seconds, exit
   139 on a Metal assertion during teardown. A 647-character plain-prose
   prompt answers in 69 seconds, so the length is not the cause. An
   ASCII-only rewrite of the eval prompt stalls too, so the em dash, the
   `<name>` and the `\n` are not the cause.
2. **The composition.** MEASURED as clear. See the Tests section.
3. **The process.** MEASURED as clear. The sample above ran inside

### Why this is separate from `^s0bw5cv`

`^s0bw5cv` is the wrong default: the `4bit` build does not generate for
anybody. This card is the ceiling: `mxfp4` generates for both the CLI
