title: 'bench: install the `packages` word list of a spec, so 105 instances get their test tools'
---
## What this is

`bench/swebench_venv.py` installs the `pip_packages` of a spec, and the
requirements file when `packages` names one. That is what the card
[[bench-prepare-the-instance-environment-in-the-driver]] asks for, word for
word, and it is what that work does.

But `packages` takes a third form, and this work does not read it. The value
is then a list of conda package names, separated by spaces:

| Repository | The value of `packages` | Instances of Lite |
|---|---|---|
| sympy/sympy | `mpmath flake8` | 76 |
| scikit-learn/scikit-learn | `numpy scipy cython pytest pandas matplotlib` | 19 |
| psf/requests | `pytest` | 6 |
| scikit-learn/scikit-learn | `'numpy==1.19.2' 'scipy==1.5.2' 'cython==3.0.10' ...` | 4 |
| astropy/astropy | `setuptools==38.2.4` | 2 |

## Why it is a problem

None of those 105 instances gets `pytest` from its `pip_packages`, and each of
them has `pytest -rA` as its `test_cmd` (sympy uses `bin/test`). Measured on
this machine on 2026-09-12, with a real build of `psf__requests-2317`:

```
status built python 3.9 seconds 2.4
import requests -> ok
python -m pytest --version -> No module named pytest
```

The environment imports the package, and the agent still cannot run one test
of the instance. The agent then installs pytest itself, which is the work
that the environment step exists to remove.

## The work

- Install a `packages` value that is neither `requirements.txt` nor
  `environment.yml` with the pip of the environment of the instance.
- Read the value with `shlex.split`, because one value of scikit-learn holds
  quoted names: `'numpy==1.19.2' 'scipy==1.5.2'`.
- Leave `environment.yml` as it is. It is a conda file, and pip cannot read
  one. 27 instances name it.
- Add a test for each of the three forms, beside the tests that are there.
- Build one real `psf__requests` instance by hand, and prove that
  `python -m pytest --version` answers in its environment.

## What to watch

A conda name is not always a PyPI name. Each of the names in the table above
is on PyPI, so this should hold for the Lite split, but a build that fails
here must give the record row the reason, exactly as the other build failures
do.
